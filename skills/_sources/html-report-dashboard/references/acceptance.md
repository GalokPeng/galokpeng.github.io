# Report acceptance: evidence, interaction, and failure

Validate what this particular report includes. Do not add widgets to satisfy a checklist. Run `node <skill>/references/validate_report.mjs <report.html>` as a structural check, not as evidence that the UI works. Use `--strict` when the report should be wholly offline and warnings should fail validation. The bundled browser script tests the starter; adapt it or add target-specific tests for a report.

1. **Numbers:** independently recompute at least one main result, its denominator and coverage. Reconcile totals, region membership, axes or transitions, as relevant. Confirm chart and table show the same series. Settled contradictions should surface as explicit discrepancies, not get normalized away.
   - For a quantitative Venn, check actual circle and intersection areas against the counts/weights on a common scale (not just the labels). Include an unequal-size case, verify exclusive regions, and test an unrepresentable case renders a usable exact table or UpSet with no misleading circles.
2. **Clicks and IDs (interactive):** from the actual overview rather than by calling a state function, click a nontrivial result. Assert exact matching record IDs, scope, count and active chips. Check a second result (ideally same count but different IDs), an empty result, an additional filter, and return state. If evidence is sampled, assert both counts and that the displayed IDs are a subset. Test keyboard activation too. For a repair, reproduce the prior issue before changing the code when practical.
3. **Readability and layout:** open as `file://`. At representative desktop and narrow sizes (e.g. 1440 and 390px) inspect longest text, side-by-side comparisons, chart labels, and overflow. After tapping a result or opening a record, verify its heading and start of the relevant content actually enter the viewport; a DOM element can be “visible” to a test API yet sit below the fold. Verify the drawer has room for its content, close/action controls stay visible with scrolling, and the list remains operational afterward. Test a large zoom or an intermediate breakpoint when the content is dense. Inspect actual screenshot(s) or rendered DOM measurements; don't claim visual inspection if only metrics were checked.
4. **Accessibility/runtime:** check first visible content, focus-visible cues, Tab/Enter, Escape, focus restore, and relevant Arrow/Home/End tab behavior. Check light and dark if present, reduced motion if animated, zero uncaught runtime errors, and the static fallback with JS disabled or initialization deliberately failed. If browser automation is unavailable, state what was covered by static/manual checks and what wasn't verified.
   - For an overlay drawer with a backdrop, click or tap outside, confirm it closes and restores filters and focus, and check the click did not trigger the underlying UI. Also verify an inside click and a text-selection drag from inside to outside both leave it open. Test the visible close button at full width where there is no exposed backdrop.
5. **State and review (if present):** input/review must not rebuild and steal focus; autosave survives reload where supported, has visible status and export fallback, and never overwrites original labels. Verify import → export round trip by comparing IDs, notes, label sets, originals and rejected/nonmatching rows.
6. **Safety and offline:** no dependency on networking when offline was requested. Include an inert literal HTML/JS-looking string (e.g. closing script markup) in a synthetic validation fixture; assert it renders only as text and JSON remains valid. Avoid external navigation from raw untrusted input. Confirm large files stay usable and no raw evidence was silently shortened.

Handoff should link the actual file, provide key coverage/limitations, and state whether the tests ran in a real browser. Keep the main result and caveats inside the report so it stands alone.
