# 软件产品全链路交付

让交付结果可执行、可验证、可恢复。适用于新产品、既有产品迭代、发布工程和正式上线。支持单仓库、多仓库与混合产品；不指定语言、UI 框架、代码托管或云厂商。

## 先确定这次做到哪里

1. 读取工作区约定、已有架构/构建/发布文档与当前 Git 状态。确认仓库、分支、远端、未提交改动、已有标签和正在运行的应用/流水线。找不到源码时先定位，不能把工作目录名称当作项目身份。
2. 从对话和现有项目识别目标：本地验证、可分发构建、上游 PR、正式发布、生产部署，或其中几项。已有明确授权与约束继续沿用。不要重复询问；缺少真正影响下一步的信息才问一次，同时继续不依赖回答的工作。
3. 识别产品组成：桌面端、Web 前端、API/服务、移动端、CLI、库、扩展、后台任务，以及官网/下载/更新服务。每个组成可有自己的仓库、提交和部署，不能强行归为一个 SHA。
4. 写下精简交付契约：用户任务、验收行为、支持平台、数据边界、目标环境、版本来源、发布权限、验收证据、回退方式。优先补充已有文档；确有需要才复制 [交付契约模板](assets/templates/delivery-contract.md)。
5. 根据本次目标选门禁。普通修复只走相关步骤；本地测试不触发推送、发布、生产部署或版本递增。“做网站”不等于同意购买域名，“准备发布”不等于已经授权公开发布。

账号已登录只说明凭据可能可用，不能证明目标组织、生产环境或付费操作已获授权。Skill 不授予额外权限，也不要求安装自身或其他 Skill。工具不具备某能力时换用可用的等价方式，并如实保留未验证项。

## 不可混淆的四个维度

- **范围**：本次究竟交付哪些组成与渠道。
- **授权**：允许改本地、推分支、开 PR、合并、公开发布、部署到哪个环境；这些彼此独立。
- **验证**：每个门禁的 `pass / fail / pending / not_applicable`，以及与候选提交/制品对应的证据。
- **对外状态**：未公开、发布中、部分完成、已公开、已撤回、等待外部审核。

通过测试不自动授权发布；已获发布授权也不能跳过失败的测试。未纳入范围是 deferred，不是“不适用”。不适用必须有产品事实与理由，不能因为困难、工具缺失或失败而标记。

## 执行主线

### A. 建立基线并实现

复现用户问题或把需求转成可观察验收条件；记录已有正常行为和数据兼容要求。依现有代码优先实现最小完整路径，再覆盖错误、取消、重复操作和退出恢复。跨进程/网络/原生接口用实际测量决定隔离、线程和语言边界，不把个人技术偏好变成统一架构。

保留用户未提交工作，使用合适的现有检出或按项目约定隔离。不得为清理工作区擅自 reset、stash、删除数据或覆盖输出目录。

### B. 证明代码与制品都能用

按风险运行相关测试和必需回归。测试的是实际行为、数据与失败边界。源码测试通过之后，还要验证拟发布的可执行文件、包、容器或部署；不能让开发环境的 PATH、全局包和个人配置掩盖缺失依赖。

区分纯逻辑、离屏 UI、模拟平台、真实平台与物理设备验证，报告时保留限制。源码内容、制品内容、源码归属和原始字节摘要分别验证，不能用测试数量代替覆盖说明。

### C. 固化发布候选

确定版本政策和唯一版本来源；只在明确准备发布时更新正式版本。完成变更说明、迁移/兼容提示、许可材料与必要展示。确定干净候选提交、目标平台矩阵、制品清单和构建输入。

候选发生实质改变，就更新候选标识并重跑受影响的门禁。不能拿旧提交的绿灯为新提交放行。需要精确来源的制品从固定提交/受控快照构建；不能暗中打包工作区额外文件。

### D. 自动构建并按授权发布

选择一种明确的发布触发策略，保留本地/PR 检查与正式发布的权限边界。发布任务消费已校验的同一份制品，避免在上传时临时重新构建一个不同产物。签名导致字节变化时，在最终签名后生成摘要并以最终制品重新验收。

先验证制品齐全，再发布版本、提升生产部署或更新下载清单。版本标签、发布页、下载别名、官网与客户端元数据都应指向已验证的候选。多渠道无法原子切换时，先保证旧链路可用，再按明确顺序提升；如实记录暂时的不一致。

### E. 监督到可观察结果

“命令已提交”“git push 成功”“网页返回 200”都不是最终成功。跟踪准确的仓库、提交、工作流、run/attempt、制品、部署和域名，直到本次要求的门禁完成。

- 构建结束：确认必需任务真实成功，不把 skipped/cancelled 当成通过。
- 发布结束：确认正式版本可见、标签归属正确、平台制品/校验材料齐全。
- 上线结束：确认生产域名/流量实际指向目标部署，核心用户路径可用。
- 更新链路：确认客户端取得的版本、平台、渠道、大小和摘要与实际下载一致。

监测采用有间隔、可中断、受总时限约束的等待，不忙轮询。通常每隔 30–60 秒检查，按平台预计耗时调整；约 60 秒内给用户有意义的进展。遵循平台超时和任务预算，异常久未推进时查原因，不能无限重试或把等待转成永久自动化任务。

启动长任务前记录预计耗时、平台上限、本次等待/重试预算与停止条件。已明确的用户要求优先；没有约定时根据操作风险选择合理预算并说明，不能仅凭“等待”视为成功。

### F. 交付与接续

提供实际完成项、验证环境、版本/提交、可用下载或访问地址、必要限制与剩余外部依赖。部分失败时逐项说明成功与待完成的部分，不宣布整个产品上线成功。

需要跨会话接续时使用 [接续记录模板](assets/templates/handoff.md)：保存已观察事实、候选标识、授权范围、精确流水线/部署 ID、产物摘要和下一步；不保存令牌。继续前核对当前外部状态，不能照抄旧缓存结果。未明确请求时不自动创建新的长期目标、提醒或聊天。

## 每次外部变更前

检查目标身份、已有授权、候选证据、影响范围与可恢复性。范围内且已授权的正常推进不重复求确认；缺失授权时先把代码、构建、差异、预览和风险做成可审查结果，再说明要批准的具体动作。按工具的实际审批机制执行，不能绕过拒绝。

对公开上传、生产数据迁移、域名/DNS、计费、签名凭据、访问控制和不可逆删除分别判断。授权推送某个分支不等于授权修改组织权限。生产回滚也不必然可逆，先确认数据库与外部副作用。

## 附带工具的正确定位

两项工具只使用 Python 标准库，建议 Python 3.10+；缺少运行时时按同一证据规则用可用工具替代，不为运行 Skill 擅自安装环境。

下面命令相对于 Skill 目录。应用到项目时使用脚本与项目输入的实际路径；不假定当前工作目录就是项目或 Skill 根目录。

```text
python scripts/release_guard.py --manifest <证据清单.json> --artifact-root <最终制品目录>
python scripts/verify_endpoints.py --config <端点检查.json>
python -m unittest discover -s tests -v
```

`release_guard.py` 本地只读，校验清单、门禁声明、来源标识与实际文件摘要；它不会连接平台或批准发布。`verify_endpoints.py` 会发出有界的只读网络请求，检查状态/跳转/内容/摘要；它不会执行下载内容或启动安装。调用前先验证输入的目标属于当前任务。详细边界见证据协议。

正常使用时不运行 Skill 自测，除非修改了附带脚本。工具通过不能替代真实安装、数据库恢复演练、签名验证或商店审核。
