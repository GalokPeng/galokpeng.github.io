# 08 上线、监测与故障恢复

## 生产之前

确认环境、目标用户/流量、配置、secret 引用、域名、证书、数据迁移、备份/恢复、观察窗口和回退条件。仅有代码权限不等于有生产数据库或 DNS 权限。能做的预览、差异、备份校验与候选构建先完成，再针对缺失的具体授权询问。

数据库变化应考虑混合版本运行：优先按需要选择扩展→迁移→收缩，先允许旧/新客户端共存，不能在仍有旧客户端时直接删除必需字段。不可逆变更给出明确数据影响与恢复边界，必要时安排窗口与独立批准。

按实际风险选择直接替换、蓝绿、金丝雀或滚动；小型无状态产品不必引入复杂基础设施。确认健康/就绪检测检查的是业务依赖，而不只是进程存活。

## 上线后

观察真实生产入口：部署/镜像 digest、路由/域名、版本/API 兼容、关键用户路径、错误率、延迟、容量、日志与告警。移动端确认是上传、测试、审核中还是公开发布；服务进程启动不等于流量已切过去。

只采集经约定的必要遥测，避免在“完善上线”中偷偷加追踪。组织通知、邮件、社交发布、付款或新账号创建分别受授权约束。

## 失败分类与有界处理

| 情况 | 处理 |
| --- | --- |
| 网络/暂时平台失败 | 保留证据，有限次退避重试；核对是否部分完成 |
| 编译/测试确定性失败 | 修复根因，形成新候选或重验，不降低门禁 |
| 草稿/部分资产上传 | 核对来源与摘要后幂等补齐；不覆盖公开版本 |
| 官网成功、软件发布失败 | 报告部分状态，保持旧下载可用，修复发布 |
| 软件成功、官网失败 | 保留正式制品，修复部署/别名，避免重新发同版 |
| 商店/审批/凭据缺失 | 给出准确提交 ID、待办与 waiting-external，不伪称完成 |
| 生产健康异常 | 按批准条件停止推广、回退或修复，持续验证数据兼容 |

同一错误反复出现后先改变诊断或修复策略，不用无限重试消耗资源。超出本次授权、成本、任务预算或平台时限时给出可接续结果与准确状态，不把失败包装成成功。

## 回退

回退对象分别包括代码/镜像、流量、配置、数据库、下载元数据、客户端通道与外部副作用。旧二进制不一定能读取新数据；旧部署不一定恢复了旧环境变量；客户端已升级也不能假定立即降级。

回退前核对恢复点确实存在、可读且属于正确环境；需要恢复用户/生产数据时明确是否会丢失恢复点之后的新数据。不得未经授权覆盖这些新数据。没有安全降级时可撤回推广并发布修订版本，清楚告知用户。

回退后再次走实际入口与健康检查，记录恢复的候选/部署、数据版本和观察结果。事故记录写可验证根因、影响、措施和防复发检查，省略令牌与个人数据。

## 进入下一轮迭代

发布后保留反馈和缺陷入口，明确维护人与支持平台。收集最少的版本、环境、复现步骤与已脱敏诊断；安全问题走适当的私密披露渠道，不要求用户公开原始个人数据。把已确认缺陷转成可复现用例、修复与下一候选，跟踪兼容/弃用承诺及后续观察。遥测、自动崩溃上传与通知不是发布流程隐含授权。

## 最终交付

汇总范围内每一项：代码/提交、制品、发布页、官网、更新、平台/商店状态、验证限制。给用户能直接使用的链接与必要下一步。不把提交 hash、测试数量或“流水线已启动”单独当成交付。
