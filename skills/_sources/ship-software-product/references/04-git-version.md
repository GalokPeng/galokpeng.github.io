# 04 Git、贡献与版本

## 保留现有工作与身份

确认仓库根目录、分支、remote、跟踪关系、工作区与已发布标签。未提交内容先辨认来源，不默认都是本任务；只提交授权范围。遵循项目工作树和分支规则，不为便捷自动 stash/reset、强推或搬走用户文件。

现有项目二开只有在去向不明确且会影响工作时，才问一次自行维护还是贡献上游。贡献路径通常 fork/主题分支→PR→审阅→合并；有维护权限也按当前仓库规则。用户已明确作为维护者直接发布时，不能凭通用模板强迫另建 fork。

PR 写具体问题、最终行为、相关验证与限制。使用真实换行/文件方式传正文，避免 shell 转义改变内容或执行正文中的字符。不要把开发对话、废弃方案和个人数据放入 PR。

合并前核对目标分支、必需检查、审阅/Code Owner、兼容与迁移说明，以及当前授权是否包含合并。冲突按两侧意图解决，不能一律选 ours/theirs；按仓库约定 merge/rebase/squash，不擅自改写共享历史或绕过保护。最终合并提交与已测 PR head/merge SHA 不同时，按影响复验；发布必须识别最终候选。

## 版本政策

先识别项目使用 SemVer、日期版本、平台构建号或其他约定。遵循用户指定版本，并核对平台限制与已发布记录；需要改变不兼容 API、数据或包身份时明确说明。不能自动将每次提交发布为新版本。

SemVer 仅在项目采用该约定时按其公开接口定义使用：比较数字分量与预发布优先级，不能用字符串排序，也不能把 build metadata 当作更高版本。移动商店、包管理器与 Windows/macOS 的版本格式可能有额外约束，分别映射。

维护一个产品版本来源；派生显示版本、包文件名、安装器、元数据、文档标签。多组成不必共用版本号，需有可核验的组成清单与兼容关系。正式打包前核对这些映射，不对源码批量替换版本字符串。

## 发布候选不可漂移

记录候选提交、分支/标签、构建输入、锁文件与变更说明。PR 检查的 merge SHA 与最终 squash/rebase 提交可能不同，按项目门禁对最终提交复验。构建可用明确受控快照，但不能把脏工作区伪称为已提交源码。

发布标签一旦公开不重指向其他提交。已公开版本的内容不能静默替换；优先发修订版本并说明影响。失败若留下草稿，先核对其提交与已上传摘要，再补齐同一候选或按平台规则放弃草稿；不可盲目覆盖已有资产。

源码归属与二进制字节复现是两件事：记录 tag→commit、归档来源与构建 provenance。Git 属性、换行转换、时间戳、压缩器、工具链和签名会影响字节。文本可以按已知规则解释差异；制品摘要、二进制内容不能通过“统一换行”变成相同，也不能伪称做到了可复现构建。

## “只要 git push 就发布”应如何实现

选一种触发主线：受信任分支上的版本变更、受保护发布标签、明确手动发布，或经过批准的自动版本工具。说明普通提交、PR、预览与正式发布各自行为。

例如：push→检查候选版本比已发布新→构建/测试→安装或运行验证→上传同一制品→发布→部署/更新入口核验。版本未变化或已经公开时，只做适用检查，不重复发布。避免分支与 tag 两套触发同时产生重复版本，也避免旧流水线晚完成后把“latest”倒退。

自动化可以完成重复劳动；权限不足、必要审核、缺签名身份、付费账号或不可逆数据变更仍需对应授权与外部条件。
