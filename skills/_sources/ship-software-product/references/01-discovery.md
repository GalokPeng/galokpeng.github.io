# 01 发现与交付契约

## 从现状得出最少必要决策

先看源码、文档、清单、锁文件、CI 与部署配置，不从历史口述猜当前事实。仓库工具/连接器能提供的信息先查，避免让用户重复提供。

记录：产品组成与用户任务；分发对象；支持 OS/架构/浏览器/设备；在线/离线条件；数据归属与敏感性；现有用户/安装；已有版本和发布渠道；维护者希望自行维护、贡献上游还是正式上线。

新项目先做到一条完整可验收路径。既有项目先复现问题或测量缺口，别因为使用本 Skill 就重建目录、改语言或引入额外服务。技术方案比较至少覆盖运行成本、依赖体积、性能、可维护性、分发限制与团队能力；原生/跨平台/解释型方案以瓶颈实测取舍。

不清楚的情况分两类：

- 可逆的实现选择：依据现有项目做合理决定，记录关键假设。
- 会改变产品、数据、公开范围、成本或生产目标的选择：需要用户明确；等待时继续准备独立工作。

## 按产品形态裁剪交付

| 形态 | 重点验收 | 不应无故强加 |
| --- | --- | --- |
| 桌面 | 平台/架构、依赖、DPI/输入、安装升级卸载、后台资源释放 | Web 后端、每次启动联网、依赖用户另装开发工具 |
| Web 前端 | 构建、路由、真实域名、浏览器/移动布局、缓存、核心交互 | 桌面 Setup、自更新安装器 |
| 服务/API | 配置/密钥、健康与就绪、鉴权、迁移、观测、流量与回退 | 必须有营销官网或复杂微服务 |
| 移动端 | 包名与签名、设备、权限、商店构建号、提审/灰度、旧客户端兼容 | 把上传测试渠道说成应用商店公开上架 |
| CLI | 安装/升级路径、shell/平台、退出码、stdout/stderr、非交互行为 | 图形界面或常驻服务 |
| 库/SDK | 公开 API、兼容性、依赖/类型、构建产物、注册表发布与安装导入 | 官网、图形安装向导、客户端自更新 |
| 扩展/插件 | 宿主兼容、权限、签名/审核、商店状态、更新机制 | 宿主不允许的自行覆盖更新 |
| 固件/嵌入式/驱动 | 硬件身份、签名/引导链、断电恢复、台架与真实设备、刷写回退 | 把普通发布授权扩展成刷写真实设备 |
| 混合产品 | 组成之间的版本/API/数据兼容及依赖顺序 | 一个 SHA 覆盖所有独立仓库的证据 |

内网软件可以没有公共下载地址；闭源软件可以不公开主仓库；没有自动更新的产品可提供受支持的手动升级。这些是契约选择，不能因模板默认值而改变。

医疗、金融、工控等受监管或安全关键产品需额外识别适用标准、审核人与验证环境。本 Skill 的通用门禁不能代替行业认证或专门安全论证。

## 约定停止点

本地交付：功能与本地证据即可，不递增公开版本、推送或部署。候选交付：提供可安装/运行的候选和预览，不开放生产入口。正式交付：按明确范围验证发布与生产结果。移动商店审核等不可控制步骤标记 waiting-external，附提交 ID 与待办；不伪造终态。

跨会话的授权要保留具体目标、分支/环境、渠道和边界。用户后续“暂不发布”收窄范围，不能被更早的“全权负责”覆盖。

## 最小文档

优先维护项目已有对应材料：产品/验收说明、架构决策、开发命令、测试说明、版本与发布操作、运维恢复说明。小项目可以合并成一份；关键是命令可执行、路径存在、事实可核对。不要为填模板写空文件。

为后续 Agent 保留简洁入口（例如既有 AGENTS.md 或开发指南）：领域/模块地图、启动与验证命令、数据隔离、版本来源、发布权限与恢复入口。记录稳定约定，当前候选和临时进度放接续记录，不把一次故障或聊天偏好变成永久通用规定。
