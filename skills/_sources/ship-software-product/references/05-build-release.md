# 05 构建、分发与 CI/CD

## 固定输入与输出

为候选确定平台矩阵、锁文件、编译器/SDK、打包器、原生组件、运行时与资源清单。使用可核验来源、摘要或不可变引用；下载有大小/时间上限，源码备用来源同样验证，不执行备用压缩包中的任意脚本。

输出以交付形态裁剪：安装包/便携包/应用包、容器 digest、包管理器工件、静态站点、移动商店构建或 SDK 包。必要时附源码、对应组件源码、校验值、签名、SBOM、许可证和构建说明。没有需求的形式不强行生成。

构建输出与用户数据分开；若输出目录含真实配置，不能删除重建或再次打包。检查 `.env`、凭据、私钥、历史数据库、日志、个人截图及缓存是否意外进入产物。包能构建不代表包内容正确。

## 推荐流水线职责

1. **Plan**：解析唯一版本、候选与目标矩阵；核对发布资格、授权通道和已发布状态。
2. **Check**：运行适用测试、静态/配置验证、文案/资源与文档链接检查。
3. **Build**：在受控环境产出固定候选的制品，记录工具链和输入来源。
4. **Verify artifact**：对最终包做启动、安装/升级/卸载、签名/内容和关键功能验证。
5. **Publish/promote**：消费已验证制品，不重复构建；校验上传前后摘要，再公开/提升。
6. **Verify public result**：检查标签、版本/渠道、分发物、真实下载、域名、更新元数据与运行健康。

这是职责边界，不要求必须六个 job。小项目可以合并，复杂产品可拆矩阵；任何简化都不能省略适用的事实验证。

## 权限和供应链

PR/不受信任贡献默认不能获得生产、签名或发布凭据。不要在高权限上下文检出并运行未审代码。限制 publisher 权限与可访问环境，优先短期身份/OIDC或平台托管凭据。固定工作流依赖到可验证的不可变引用；如平台提供等效依赖锁，按当期官方规范验证，不复制未经核对的 SHA。

不要把登录口令、token、私钥、带签名下载地址写入仓库、日志或演示素材。签名密钥与代码发布权限分开；变更仓库策略、环境保护或计费设置不能被常规发布授权自动覆盖。

许可证清单来自实际分发物，包括动态库、插件、编译器运行库、字体、图标、模型和媒体；“主源码许可”不能替代组件义务。需要对应源码时提供与组件版本、构建选项相符的材料。签名/公证/商店要求以目标平台当前规则为准，不能假称已签名。参见 [权威来源](sources.md)。

## 重试与并发

为同一产品/渠道串行化最终发布或使用平台幂等机制；平台/架构构建可以并行。验证需要的 job 和矩阵是否全部结束，skipped 只有契约明确允许时才成立。

识别 run ID、attempt、触发提交、目标环境、产物版本与 digest；同名成功任务可能属于旧提交。重跑只作用于允许重试的阶段；上传、标签、数据库、通知和生产提升先检查是否已发生。

取消旧流水线前确认它属于当前授权任务且尚未执行不可中断副作用。不能为清队列取消他人的发布或正在迁移生产数据的任务。网络/超时可做有界退避重试；同一确定性失败需修复，不重跑掩盖。

## 发布应满足的事实

使用 GitHub 时，先按契约列出必交文件及目标位置。构建任务完成所有打包后，汇总最终文件并生成 SHA-256 清单；发布任务下载对应 run 的产物，逐个校验并上传到目标 tag 的 Release。独立的 Actions artifact 可以保留供人工交接。最终从 Release 附件列表核对预期文件名、大小与摘要，并从用户下载入口取回关键附件。Actions 下载的 ZIP 和其中的安装文件分别记摘要。[Actions 产物下载](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/download-workflow-artifacts) · [Release 附件接口](https://docs.github.com/en/rest/releases/assets)

遇到“Actions 有文件、Release 看不到”，按构建步骤顺序、artifact 名称及下载目录、发布任务的文件清单、公开附件依次定位。用缺少必交附件和附件字节被改动的夹具验证发布会失败。仅构建的运行可按范围跳过分发。已发布版本要补附件时先找原候选的可验证字节，核对原校验清单及项目允许的补发方式；需要用改过的代码重建时使用新的修订版本。

已有 GitHub CLI 时，可用下面两条只读查询定位差异。把大写占位符替换为已核验的仓库、run ID 和 tag。第一条返回该次运行的临时工件及过期状态，第二条返回发行页的附件状态、大小和平台提供的摘要。需要确认具体 attempt 时再核对任务详情和工件来源；缺少远端摘要时按可信清单实际下载复算。

```sh
gh api --paginate repos/OWNER/REPO/actions/runs/RUN_ID/artifacts --jq '.artifacts[] | {name, expired, digest}'
gh api repos/OWNER/REPO/releases/tags/TAG --jq '.assets[] | {name, state, size, digest}'
```

附件较多时，对 Release 使用分页的 `releases/RELEASE_ID/assets` 接口。项目若采用不可变发布，可先在草稿中组装并核对全部附件，再公开并从下载端复核。

正式版本不是 draft、没有误标预发布；tag/registry/build 来源对应候选；所有目标平台的必要制品存在、大小合理、摘要/签名一致；友好文件名或 latest 别名若存在，与版本化文件实际内容相同。上传一半不能算成功。

对代码、运行产物、官网、更新服务分别记录版本/部署状态。公开后发现缺陷先评估影响，必要时停止推广或撤回候选，按 [恢复流程](08-operations.md) 处理，不能偷偷修改公开旧版。
