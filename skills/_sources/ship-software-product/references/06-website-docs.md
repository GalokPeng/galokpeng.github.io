# 06 README、官网与下载体验

## 内容与产品一致

README 至少让目标用户知道：软件解决什么、当前支持什么平台、如何安装/运行、如何升级、数据放哪里、关键限制、许可、反馈入口。面向开发者补充可执行的开发与验证命令。现有文档足够时只维护，别复制成多套相互漂移的介绍。

官网服务使用决策：主要能力、可信展示、支持系统、下载/访问/注册入口、更新说明与反馈。用户选择技术栈/托管平台优先；不为了网站强迫引入新后端、账号、付费服务或重建品牌。

自动跟随系统与手动切换的语言/主题关系明确；覆盖应用、安装器和官网中本次要求的范围。区分产品已支持与未来计划，不用路线图冒充现成功能。

## 展示素材

截图来自隔离演示配置，或由产品真实组件配合虚构数据生成；概念图、放大示意和真实截图分别标注。不展示私人桌面、文件名、头像、通知、路径、访问记录、剪贴板或 token。检查图片内容、元数据、文件名及 HTML alt。

多语言、明暗、DPI/长文字/窄屏按目标验证。检查文本对比度、键盘焦点、替代文字、减少动画偏好、图片体积和加载策略。截图文件存在还不够，实际页面不能拉伸、错裁、溢出或链接失效。

## 下载必须到真正的产品

若按钮承诺“下载安装包”，最终应取得正确系统/架构/渠道的制品，不能只跳到代码仓库首页或版本介绍页。移动端/商店产品则指向实际商店或测试渠道；Web 产品直接进入可用产品。

优先使用稳定且版本可解析的下载元数据/服务，避免营销页硬编码易过期的版本。规范文件名、Content-Disposition、重定向与缓存行为；默认官方来源，除非用户明确选择了其他来源策略。用户可切换线路，失败时有清晰重试。

不要把 HTTP HEAD 的行为假设成 GET：端点可能用 HEAD 返回元信息，却用 GET 重定向下载。按协议分别验证方法、状态、Location、版本和最终字节。HTTP 200 也可能是错误 HTML、登录页或缓存旧页面。

官网版本介绍先上线、制品后上传时，旧下载必须仍有效，不能让“最新”指向尚不存在的文件。更稳妥的方式是：制品就绪后提升元数据/官网，或让页面只展示经验证的当前稳定版本。不要仅为消除短暂缓存不一致就重发或覆盖版本。

## 部署是独立交付项

检查正确账号、项目、仓库、分支、构建根目录、命令、输出目录、环境变量、预览/生产、域名和证书。登录状态不是正确项目的证据。先部署预览并检查核心交互，生产操作按已有授权执行。

部署返回成功不表示生产域名已切换。核对 deployment ID/commit、域名别名、HTTPS、路由、静态资源、缓存头及客户端元数据。多语言路由、相对链接、404 和 SPA 回退要符合产品行为。

恢复旧部署可能只改变流量别名，不恢复数据库、外部状态、环境变量或签名密钥。生产回滚后重新检查核心路径与下载/更新一致性。
