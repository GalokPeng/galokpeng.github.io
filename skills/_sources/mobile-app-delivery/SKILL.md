# 移动应用交付

按用户指定的平台、功能和分发对象交付。先弄清“谁会通过什么方式把哪一版装到哪里”，据此决定构建和签名。已有项目从当前阶段接手；单平台请求只执行该平台的流程。

## 从需求到可构建的应用

1. **确定交付条件。** 从对话、仓库和已有发布配置确认目标平台、手机或模拟器、分发方式、新装或升级，以及最终用户要完成的核心动作。“给我一个安装文件”通常优先考虑本地安装或已登记设备测试。商店提交、开启外部构建服务、注册新设备与分发给他人，依据用户实际授权执行。
2. **确认工程和构建环境。** 检查当前改动、工程入口、锁文件、构建脚本和 CI。查明 Android 模块与 variant、iOS workspace 或 project 与 scheme，以及当前环境实际具备的 SDK、构建主机、设备和签名渠道。对于更新，先从旧包或发布记录确定应用标识、构建号、分发身份和需保留的数据。
3. **实现并尽早走通一个端到端流程。** 新项目按原生能力、离线要求、已有人员和工具选择技术栈。已有工程沿用其正常构建入口。把核心需求写成手机上可观察的操作与结果，从启动、完成一次关键操作走到保存或反馈。摄像头、麦克风、定位、登录、付费等实际依赖要经过对应的平台桥接、权限或服务配置；按项目需要覆盖拒绝权限、网络变化、恢复和重试。仅打包时直接进入构建阶段。
4. **用发布配置构建。** 从仓库确定入口，锁定实际使用的变体、依赖与 SDK。Flutter、React Native、Expo、Capacitor 等使用其现有发布流程，保留原生工程定制。不要把生成目录覆盖掉手工修改，或将某个项目的脚本当作所有框架的前提。新版本写到明确的输出位置，保留上一可用版本，以便核对升级。

## 按平台签名和检查

- **Android** 交付 APK、区分 AAB／拆分包、核对发布证书和覆盖安装时，使用 [Android 交付](references/android.md)。
- **iOS** 归档真机应用、选择登记设备／TestFlight／商店分发、核对授权与嵌套签名时，使用 [iOS 交付](references/ios.md)。
- **可跨平台复核的包信息** 使用本技能的 [包检查脚本](scripts/inspect_artifact.py)。从技能目录运行 `python scripts/inspect_artifact.py PATH_TO_PACKAGE`。多个路径可一并传入。需要验证 Android 签名时加 `--build-tools SDK_BUILD_TOOLS_DIR`，并让 Java 对 SDK 工具可用。脚本只读，仅需 Python 标准库。退出码 0 表示所选检查完成；签名和实装证据分别看 JSON 字段与设备记录。
- **缺少某一平台条件时** 先查已有的授权构建主机、仓库发布流程或用户提供的签名渠道。还缺条件就完成另一平台及所有可执行检查。只有已构建出有效设备程序时才可交付待签名包，并在文件名和说明中标明状态。记录具体欠缺的材料和继续的位置。构建过程通过钥匙串、安全变量等已有通道取用密钥和口令。交付清单只记录公开的签名指纹与授权结论，渠道要求嵌入的描述文件由原生导出流程处理。

## 验收最终文件

- **从最终文件出发。** 交付前重新计算文件 SHA-256，核对应用标识、版本和渠道。开发服务器、本地源码和过去版本上的测试须单列。若应用依赖打包的静态资源、数据库或原生库，从包中验证关键资源或清单。修复后二次打包要重做受影响的检查并更新哈希。
- **安装与升级。** 有获授权的测试设备时，用这次签名的包冷启动，走完核心动作，退出或强制停止后重开。更新任务有旧版时，先在测试环境创建可识别的旧数据，再覆盖安装，检查数据和身份延续。保留用户设备上的真实数据。分别记录 Android 模拟器、iOS 模拟器和实体手机所得证据。iOS 模拟器走单独的模拟器构建。
- **按证据交付。** 对每个平台列出文件链接、版本与构建号、应用标识、SHA-256、分发方式、签名验证结果、实际验证设备及关键操作。区分“文件已生成”“签名已核验”“在指定设备已安装并跑通”。若授权走 TestFlight 或商店，另列实际达到的上传、处理、审核、可安装阶段。尚缺条件时写明对用户安装的影响。
